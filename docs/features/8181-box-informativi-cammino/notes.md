# Notes — Box Informativi (Cammini Builder)

## Deviazioni dal piano

- **`phpunit.xml` non va modificato**: il piano originale non lo prevedeva, ma senza aggiungere `wm-package/tests/Feature` alla testsuite "Feature" di camminiditalia, `php artisan test --filter=...` non trova i test in quella cartella. La modifica è stata fatta (senza saperlo, non riportata) durante il Task 1, poi scoperta e **revertita** durante la review finale: la review formale ha rilevato che includere l'intera cartella nella discovery automatica trascina dentro 16+ test preesistenti e rotti (`Wm\WmPackage\Tests\TestCase` non autoloadabile da camminiditalia, bug noto oc:8231) e alcuni con `RefreshDatabase` su un `phpunit.xml` che non isola il DB di test da quello di sviluppo (rischio già documentato in `wm-package/CLAUDE.md`). **Soluzione adottata**: nessuna modifica a `phpunit.xml`, i test si lanciano per path esplicito, stesso pattern già in uso per `LayerLogoFieldValidationTest.php`/`AbstractUserResourceImpersonateTest.php`:
  ```bash
  docker exec laravel-camminiditalia php artisan test \
    wm-package/tests/Feature/Nova/ConfigDetailResolverTest.php \
    wm-package/tests/Feature/Nova/InfoBoxItemRepeatableTest.php \
    wm-package/tests/Feature/Nova/LayerConfigDetailInfoBoxTest.php \
    wm-package/tests/Feature/Nova/EcTrackEcPoiConfigDetailTest.php \
    wm-package/tests/Feature/Nova/ConfigDetailAuthorizationInheritanceTest.php
  ```
- **`title` deve passare da `decodeTranslatableValue()`**, non da un semplice `is_array()` check: senza questo, `title` salva tutte le lingue configurate anche vuote (il widget `KeyValue` sottostante di `HasFlexibleTranslatableFields` le riempie sempre di default), mentre `content` le filtra — un'asimmetria che avrebbe rotto proprio l'allineamento con `config_home` richiesto esplicitamente dallo scrum. Trovato e corretto in fase di review finale.
- **Il resolver non è un `jsonb_set` SQL atomico** come inizialmente concordato durante la fase di Challenge: dopo aver letto il codice vendor (`Whitecube\NovaFlexibleContent\Flexible::fillAttribute()`), si è verificato che `set()` gira PRIMA di `$model->save()` — una query raw lì dentro verrebbe sovrascritta dal successivo save standard di Nova. Il resolver usa invece l'assegnazione nativa Eloquent (`$resource->{'properties->config_detail'} = $data`), che delega a `HasAttributes::fillJsonAttribute()` il merge sibling-preserving — stesso pattern già in uso per ogni altro campo `properties->*` del progetto.

## Bug trovati

- **Bug nel piano stesso** (non nel codice applicativo): il piano indicava l'import `use Laravel\Nova\Fields\Repeater\Repeater;` — classe inesistente in Nova 5.7.6. Corretto in `use Laravel\Nova\Fields\Repeater;` (il campo Repeater vive direttamente nel namespace `Laravel\Nova\Fields`, non in un sotto-namespace `Repeater\`). Trovato e corretto identicamente in Task 3 e Task 4.
- **Bug nei test di esempio del piano**: gli assert su `Layout::getResolvedValue()['attributes']` assumevano una mappa piatta `{label: value}`, ma quel metodo restituisce in realtà un array di field Nova serializzati (`{attribute, value, component, ...}`). Corretto ovunque cercando il field per `attribute` e leggendo `value`.
- **`KeyValue::fillAttributeFromRequest()` richiede una stringa JSON**, non un array PHP grezzo, per il campo `title`. I fixture dei test costruivano l'input come array — corretto con `json_encode()`.
- **`EcTrack::factory()->create()` (non `createQuietly()`) innesca una chiamata di rete reale** verso `https://dem.maphub.it` tramite `EcTrackObserver::created()` sotto `QUEUE_CONNECTION=sync` — non correlato a questa feature, aggirato con `createQuietly()` nei fixture di test dove non serve l'observer.
- **`putJson()` su un endpoint Nova rompe silenziosamente il payload**: `whitecube/nova-flexible-content` clona la request in una `ScopedRequest` che, per richieste JSON, condivide per riferimento il `ParameterBag` con la request originale (comportamento di `Request::createFrom()`/`replace()`) — il campo `config_detail` risulta silenziosamente vuoto anche con risposta 200. Non è un bug di produzione (il frontend Nova reale invia sempre FormData, mai JSON puro, su questo endpoint), ma va tenuto a mente scrivendo altri test HTTP su `nova-api/*`: usare `->put()` (form-encoded), non `->putJson()`.

## Decisioni

- **Correzione architetturale post-Challenge** (arrivata da un secondo giro di scrum, dopo l'approvazione iniziale dell'overview): la struttura è stata riallineata esplicitamente a `config_home` — chiave discriminante `box_type` (non `type`), valore layout `info` (non `info_box`), e campi tradotti come oggetti annidati per lingua (`title`/`content` = `{it, en, ...}`), non chiavi sorelle con suffisso lingua. Il dettaglio del confronto è in `overview.md`.
- **Nessun preset Nova custom per il Repeater**: verificato che il preset `JSON` di default di Nova già round-trippa la forma `{type, fields}` attraverso `Layout::getAttributes()`/`duplicateAndHydrate()` senza adattamenti — tutta la logica di reshape (Nova-internal ↔ `{title, content}` persistito) vive nel `ConfigDetailResolver`, non in una classe preset separata.
- **HTMLPurifier istanziato una sola volta per chiamata a `fields()`** (non per riga/lingua), con `Cache.SerializerPath` esplicito su `storage_path('framework/cache/htmlpurifier')` — evita di dipendere dalla cache di default di HTMLPurifier dentro `vendor/`, non scrivibile su deploy con vendor rigenerato/read-only.

### Rifiniture UI post-esecuzione (richieste ad-hoc dal dev, non nel piano originale)

- **Panel/campo rinominato da "Box Informativi" a "Blocchi Dettaglio"**: il nome originale duplicava tre volte lo stesso testo (Panel, campo Flexible, bottone "Aggiungi Box Informativo") ed era fuorviante — il contenitore è generico (`config_detail`, pensato per ospitare più `box_type` in futuro), "Box Informativo" resta solo il nome del layout/tipo di blocco registrato oggi. `Panel::make(__('Blocchi Dettaglio'), ...)` + `Flexible::make(__('Blocchi Dettaglio'), 'properties->config_detail')`, `addLayout(__('Box Informativo'), 'info', ...)` invariato.
- **Posizionamento del panel per risorsa** (richiesto esplicitamente dal dev, non "in fondo" come da wiring originale del piano): su `Layer` subito dopo il panel "Properties"; su `EcPoi` subito dopo il panel "Form" (poi ulteriormente spostato subito **prima** di "Taxonomy Poi Types"); su `EcTrack` (che non ha alcun panel "Properties") subito prima del `Tab::group('Details')`.
- **Estratto `Wm\WmPackage\Nova\Traits\HasConfigDetailPanel`** (usato da `Layer`, `EcTrack`, `EcPoi`) per eliminare la tripla duplicazione del blocco Panel/Flexible/preview — singola fonte di verità per campo editabile + preview detail.
- **`Flexible::fullWidth()` obbligatorio** quando il campo vive dentro un `Panel::make()` (non un `Tab`): verificato che `config_home` non ha questo problema perché vive dentro `Tab::make('home', ...)` (App.php), mai in un Panel — i Panel di Nova usano una griglia a due colonne (etichetta|campo) che stringe/taglia contenuti larghi come la tabella `KeyValue` di `title` e l'editor Trix di `content` annidati nel Repeater. `Flexible::fullWidth()` (alias `stacked()`, già esistente nel vendor Whitecube, mai usato prima in questo progetto) replica il comportamento "a piena larghezza, etichetta sopra" che il campo ha naturalmente dentro un Tab.
- **Preview HTML in detail raggruppata per `box_type` group, non un elenco piatto**: ogni gruppo Flexible (istanza separata creata in Nova, es. "informazioni generali" vs "tappe") viene racchiuso in un contenitore visivamente distinto (bordo più marcato) con etichetta `#N Box Informativo` (stesso testo che Nova mostra già in edit form per il gruppo, per coerenza) — altrimenti tutti gli item di tutti i gruppi apparivano come un'unica lista piatta indistinguibile.
- **Ogni item nella preview di detail è un accordion nativo `<details>`/`<summary>`, chiuso di default**, con icona chevron (▶, entità HTML `&#9656;`) che ruota di 90° all'apertura via CSS (`details[open] .wm-config-detail-chevron{transform:rotate(90deg)}`). Nessun JavaScript: un `<script>` iniettato via `asHtml()`/innerHTML di Nova non verrebbe eseguito dal browser (limitazione nota di innerHTML), ma `<details>` è comportamento nativo HTML e un tag `<style>` iniettato via innerHTML **viene** applicato normalmente (verificato) — quindi CSS scoperto per la rotazione della chevron funziona senza bisogno di JS.
- **Ordinamento chiavi JSON (`box_type` non sempre come prima chiave nel DB)**: verificato via SQL diretto che è un comportamento intrinseco di PostgreSQL `jsonb` (canonicalizza le chiavi per lunghezza, non per ordine di inserimento — `'{"box_type":"info","items":[1,2]}'::jsonb::text` produce `{"items": [1, 2], "box_type": "info"}`). `config_home` non lo manifesta solo perché `apps.config_home` è una colonna `text` (stringa opaca mai riparsata), non `jsonb`. Non è un bug del resolver (che infatti costruisce l'array PHP con `box_type` per primo) e non è risolvibile senza cambiare il tipo della colonna `properties` — nessun impatto funzionale, un oggetto JSON non ha un ordine di chiavi significativo per nessun consumer.
- **[RISOLTO] Stringhe UI riallineate al pattern di traduzione del progetto**: le prime versioni passavano direttamente il testo italiano come argomento di `__()` (es. `__('Blocchi Dettaglio')`, `__('Elimina')`) senza alcuna voce nei file di traduzione — bug di pattern, scoperto rileggendo `resources/lang/it.json`/`en.json`: la convenzione del progetto è chiave in **inglese** passata a `__()`, con traduzione italiana in `it.json` e valore identico (pass-through) in `en.json` (es. `"Cancel": "Annulla"` già esistente, riusato invariato). Tutte le stringhe introdotte da questa feature sono state rinominate a chiavi inglesi e le traduzioni aggiunte in entrambi i file:

  | Chiave (`__()`, inglese) | it | Uso |
  |---|---|---|
  | `Detail Blocks` | Blocchi Dettaglio | Panel + campo Flexible |
  | `Info Box` | Box Informativo | Layout/tipo di blocco registrato in `addLayout()` |
  | `Add Info Box` | Aggiungi Box Informativo | Bottone del builder Flexible |
  | `Are you sure you want to delete this box?` | Sei sicuro di voler eliminare questo box? | Messaggio di conferma rimozione gruppo |
  | `Delete` | Elimina | Bottone conferma rimozione |
  | `Detail Blocks Preview` | Anteprima Blocchi Dettaglio | Campo HTML di sola lettura in detail |
  | `No blocks configured.` | Nessun blocco configurato. | Stato vuoto della preview |
  | `Content` | Contenuto | Etichetta campo Trix per lingua in `InfoBoxItemRepeatable` |

  `Cancel`, `Title`, `Items` riusano chiavi già esistenti nel progetto (nessuna nuova voce necessaria). Verificato con `app()->setLocale('it'|'en')` + `__()` diretto in tinker che entrambe le lingue risolvono correttamente. Solo `it`/`en` sono lingue disponibili per l'interfaccia admin di Nova in questo progetto (`resources/lang/` ha solo questi due file) — da non confondere con le 5 lingue di `wm-tab-translatable.locales` (it/en/fr/es/de), che riguardano invece il **contenuto** dei box (title/content), non l'interfaccia Nova stessa.

## Follow-up (debito tecnico noto, non risolto in questo ciclo)

- **[RISOLTO in un secondo passaggio UI]** Il gruppo `info` in detail view mostrava box vuoti (`Repeater` in `onlyOnForms()` di default, filtrato da `Flexible::isShownOnDetail()`). Soluzione adottata: il campo `Flexible` resta esplicitamente `->onlyOnForms()`, e un campo HTML separato di sola lettura (`Text::make(...)->asHtml()->onlyOnDetail()`, dentro `HasConfigDetailPanel::configDetailPanel()`) legge `properties->config_detail` e renderizza titolo+contenuto di ogni box in blocchi leggibili — nessun uso del preset `JSON`/`asJson()` in detail (che romperebbe con `ErrorException`, verificato). `content` è già sanitizzato da HTMLPurifier prima del salvataggio quindi viene renderizzato as-is; `title` viene escaped con `e()` perché non passa da sanitizzazione.
- **Gruppi con `box_type` sconosciuto vengono cancellati silenziosamente al salvataggio**: `ConfigDetailResolver::get()` salta ogni gruppo il cui `box_type` non ha un layout registrato, e `set()` riscrive l'array per intero dai gruppi correnti in Nova. Se un domani si aggiunge `description`/`graph` e poi si fa un deploy che non li conosce ancora, un salvataggio su quella risorsa perde quei gruppi in modo permanente. Nessun versionamento/command di recovery — debito accettato esplicitamente in Challenge, qui solo documentato.
- **[RISOLTO]** Pannello `Blocchi Dettaglio` duplicato 3 volte — estratto in `Wm\WmPackage\Nova\Traits\HasConfigDetailPanel` (usato da `Layer`, `EcTrack`, `EcPoi`), che centralizza sia il campo editabile sia la preview HTML in detail.
- **Duplicazione della fonte di verità per le lingue**: `HasFlexibleTranslatableFields::translatableFields()` legge `tab-translatable.locales` con fallback a `wm-tab-translatable.locales`; `InfoBoxItemRepeatable`/`ConfigDetailResolver` leggono solo `wm-tab-translatable.locales`. Oggi sincronizzati da `WmPackageServiceProvider`, ma un consumer che pubblica `tab-translatable.php` autonomamente potrebbe disallinearli silenziosamente.
- **[RISOLTO]** Stringhe UI senza traduzione — vedi dettaglio nella sezione "Rifiniture UI post-esecuzione" sopra: tutte le chiavi rinominate in inglese e tradotte in `wm-package/resources/lang/{it,en}.json`.
- **Lint**: `ConfigDetailAuthorizationInheritanceTest.php` aveva un ordine import non conforme a Pint (`ordered_imports`) — da sistemare con `composer format` prima del commit finale. `ezyang/htmlpurifier` in `composer.json` non è in ordine alfabetico rispetto a `config.sort-packages: true`.
- **`CLAUDE.md` non ancora aggiornato** con la riga "Feature disponibili" e le decisioni architetturali di questo ticket — da fare in Fase: update-context prima della chiusura definitiva.
